# Контекст просмотрщика обращения

`ticket/view` описывает данные и действия текущего экземпляра просмотрщика обращения.
Это публичный контракт пакета. Библиотека объявляет точки `ticket/view:header.after`,
`ticket/view:common.before`, `ticket/view:customer.after` и `ticket/view:issues.after`.
Все они предоставляют контексты `ticket/view`, `ticket/view:settings`, `user/current`,
`settings` и action scope `ticket/view`, без пользовательских контекстов полей.
Для использования в CRM ещё требуется подключить эти точки и реализовать хост.

```typescript
import {
  useActions,
  useContext,
} from '@retailcrm/embed-ui-v1-contexts/remote/ticket/view'
import { useContext as useSettingsContext } from '@retailcrm/embed-ui-v1-contexts/remote/ticket/view-settings'

const ticket = useContext()
const settings = useSettingsContext()
const actions = useActions()

await Promise.all([ticket.initialize(), settings.initialize()])

const issue = ticket.issues[0]
const status = settings.statuses[0]

if (settings.editable && !ticket.loading && !ticket.loadFailed && !ticket.pending && issue && status) {
  await actions.changeIssueStatus(issue.id, status.id)
}
```

Все поля предназначены только для чтения. Изменения выполняются действиями хоста
и сохраняются в CRM, а не в черновике редактора. Статус и ответственный относятся
к отдельному вопросу из `issues`; единого статуса или ответственного обращения
в контексте нет. Для назначения передаётся ссылка `{ kind: 'user' | 'group', id }`.

Клиент представлен полями `customer.*`, как в контексте заказа. Это разные срезы
данных одной сущности: общие поля `customer.id`, `customer.type`, `customer.email`
сохраняют имена и смысл. `customer.type` использует общий тип `CustomerType`:
`'customer'` — физическое лицо, `'customer_corporate'` — корпоративный клиент.
Отсутствие клиента определяется по `customer.id === null`; значение `customer.type`
по умолчанию — `'customer'`, как в заказе.

После идентификатора и типа клиента идут `customer.name` — отображаемое имя,
`customer.email` и `customer.phones` — доступные телефоны с каноническими номерами,
затем признаки `customer.vip` и `customer.bad`. Все поля клиента здесь предназначены только для чтения.
Например, тип выбранного клиента доступен как `ticket['customer.type']`.

`contact` и `company` — отдельные сущности. `company` обозначает компанию, выбранную
в обращении, и может отличаться от основной компании клиента. Доступ к контактным
данным определяется правами текущего пользователя. API телефонии в этот контракт
не входит; телефоны клиента и контактного лица доступны как данные.

Даты представлены строками ISO 8601 или `null`. Значения `duration` и
`remainingDuration` в SLA измеряются в секундах и отражают последний полученный
снимок, а не самостоятельно обновляющийся таймер.

Возможности указаны явными полями. В `ticket/view` находятся `canCreateEmail` и
`canCreateOrder`: они учитывают права пользователя и данные текущего обращения —
клиента, его тип и контактное лицо. `canCreateEmail` разрешает открыть форму нового
письма через `openEmailEditor`, а `canCreateOrder` — форму заказа через `openOrderForm`.
Доступность самой отправки письма форма проверяет отдельно; `canCreateEmail`
не гарантирует возможность отправить письмо. `loading`, `loadFailed` и `pending` также
относятся к текущему экземпляру просмотрщика; `pending` обозначает временную
блокировку конфликтующих действий.

Независимые от обращения поля вынесены в отдельный контекст `ticket/view:settings`
с публичным импортом `remote/ticket/view-settings`:

| Поле | Смысл |
|---|---|
| `statuses` | Общий справочник активных статусов вопросов из активных групп; не список переходов конкретного вопроса |
| `editable` | Пользователь может редактировать обращения, менять статус и ответственного вопроса |
| `commentable` | Пользователь может добавлять комментарии к обращениям |

Настройки инициализируются отдельно и обновляются реактивно. Справочник статусов
сам по себе не даёт права менять статус: для этого нужно `settings.editable`.
Флаги разрешений не учитывают временные блокировки загрузки и сохранения.
Хост повторно проверяет права и состояние при вызове действия.
При `loadFailed` ранее загруженные данные могут оставаться в контексте, но
не считаются подтверждёнными последним обновлением.

| Действие | Результат |
|---|---|
| `createComment(text)` | Возвращён идентификатор сохранённого комментария |
| `changeIssueResponsible(issueId, responsible)` | Ответственный вопроса сохранён, контекст обновлён |
| `changeIssueStatus(issueId, statusId)` | Статус вопроса сохранён, контекст обновлён |
| `openTicketEditor()` | Открыт штатный редактор обращения |
| `openTicketHistory()` | Открыта штатная история обращения |
| `openEmailEditor()` | Открыта форма письма с контекстом обращения; письмо ещё не отправлено |
| `openOrderForm()` | Открыта форма нового заказа в шторке; после сохранения CRM связывает заказ с обращением |
| `refresh()` | Обновлены опубликованные данные контекста |

`openTicketHistory()` открывает штатное окно CRM. В текущем просмотрщике нет отдельной
настройки видимости истории: сервер проверяет обычное право просмотра обращений.
Состояние открытого окна и записи истории в контекст не передаются.

Действия остаются в scope `ticket/view`; у `ticket/view:settings` действий нет.
Все действия возвращают Promise. Ошибки и недоступные операции отклоняют Promise;
показа сообщения в CRM недостаточно для успешного завершения действия. После
закрытия просмотрщика хост освобождает подписки и отклоняет последующие вызовы.

Пагинируемые списки комментариев, задач, коммуникаций и истории не входят в контекст.
Заказы, файлы, теги и пользовательские поля также пока не включены в эту версию.
