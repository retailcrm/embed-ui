# Контекст просмотрщика обращения

`ticket/view` описывает данные и действия текущего экземпляра просмотрщика обращения.
Это публичный контракт пакета. Библиотека объявляет точки `ticket/view:header.after`,
`ticket/view:common.before`, `ticket/view:customer.after` и `ticket/view:issues.after`.
Все они предоставляют контексты `ticket/view`, `ticket/view:settings`, `user/current`,
`settings` и action scope `ticket/view`, без пользовательских контекстов полей.
Для использования в CRM ещё требуется подключить эти точки и реализовать хост.

```typescript
import {
  useActions,
  useContext,
} from '@retailcrm/embed-ui-v1-contexts/remote/ticket/view'
import { useContext as useSettingsContext } from '@retailcrm/embed-ui-v1-contexts/remote/ticket/view-settings'

const ticket = useContext()
const settings = useSettingsContext()
const actions = useActions()

await Promise.all([ticket.initialize(), settings.initialize()])

const issue = ticket.issues[0]
const status = settings.statuses[0]

if (settings.editable && !ticket.loading && !ticket.loadFailed && !ticket.pending && issue && status) {
  await actions.changeIssueStatus(issue.id, status.id)
}
```

Все поля предназначены только для чтения. Изменения выполняются действиями хоста
и сохраняются в CRM, а не в черновике редактора. Статус и ответственный относятся
к отдельному вопросу из `issues`; единого статуса или ответственного обращения
в контексте нет. Для назначения передаётся ссылка `{ kind: 'user' | 'group', id }`.

Клиент представлен полями `customer.*`, как в контексте заказа. Это разные срезы
данных одной сущности: общие поля `customer.id`, `customer.type`, `customer.email`
сохраняют имена и смысл. `customer.type` использует общий тип `CustomerType`:
`'customer'` — физическое лицо, `'customer_corporate'` — корпоративный клиент.
Отсутствие клиента определяется по `customer.id === null`; значение `customer.type`
по умолчанию — `'customer'`, как в заказе.

После идентификатора и типа клиента идут `customer.name` — отображаемое имя,
`customer.email` и `customer.phones` — доступные телефоны с каноническими номерами,
затем признаки `customer.vip` и `customer.bad`. Все поля клиента здесь предназначены только для чтения.
Например, тип выбранного клиента доступен как `ticket['customer.type']`.

`contact` и `company` — отдельные сущности. `company` обозначает компанию, выбранную
в обращении, и может отличаться от основной компании клиента. Доступ к контактным
данным определяется правами текущего пользователя. API телефонии в этот контракт
не входит; телефоны клиента и контактного лица доступны как данные.

Даты представлены строками ISO 8601 или `null`. Значения `duration` и
`remainingDuration` в SLA измеряются в секундах и отражают последний полученный
снимок, а не самостоятельно обновляющийся таймер.

Возможности указаны явными полями. В `ticket/view` находятся `canCreateEmail` и
`canCreateOrder`: они учитывают права пользователя и данные текущего обращения —
клиента, его тип и контактное лицо. `canCreateEmail` разрешает открыть форму нового
письма через `openEmailEditor`, а `canCreateOrder` — форму заказа через `openOrderForm`.
Доступность самой отправки письма форма проверяет отдельно; `canCreateEmail`
не гарантирует возможность отправить письмо. `loading`, `loadFailed` и `pending` также
относятся к текущему экземпляру просмотрщика; `pending` обозначает временную
блокировку конфликтующих действий.

Независимые от обращения поля вынесены в отдельный контекст `ticket/view:settings`
с публичным импортом `remote/ticket/view-settings`:

| Поле | Смысл |
|---|---|
| `statuses` | Общий справочник активных статусов вопросов из активных групп; не список переходов конкретного вопроса |
| `editable` | Пользователь может редактировать обращения, менять статус и ответственного вопроса |
| `commentable` | Пользователь может добавлять комментарии к обращениям |

Настройки инициализируются отдельно и обновляются реактивно. Справочник статусов
сам по себе не даёт права менять статус: для этого нужно `settings.editable`.
Флаги разрешений не учитывают временные блокировки загрузки и сохранения.
Хост повторно проверяет права и состояние при вызове действия.
При `loadFailed` ранее загруженные данные могут оставаться в контексте, но
не считаются подтверждёнными последним обновлением.

| Действие | Результат |
|---|---|
| `createComment(text)` | Возвращён идентификатор сохранённого комментария |
| `changeIssueResponsible(issueId, responsible)` | Ответственный вопроса сохранён, контекст обновлён |
| `changeIssueStatus(issueId, statusId)` | Статус вопроса сохранён, контекст обновлён |
| `openTicketEditor()` | Открыт штатный редактор обращения |
| `openTicketHistory()` | Открыта штатная история обращения |
| `openEmailEditor()` | Открыта форма письма с контекстом обращения; письмо ещё не отправлено |
| `openOrderForm()` | Открыта форма нового заказа в шторке; после сохранения CRM связывает заказ с обращением |
| `refresh()` | Обновлены опубликованные данные контекста |

`openTicketHistory()` открывает штатное окно CRM. В текущем просмотрщике нет отдельной
настройки видимости истории: сервер проверяет обычное право просмотра обращений.
Состояние открытого окна и записи истории в контекст не передаются.

Действия остаются в scope `ticket/view`; у `ticket/view:settings` действий нет.
Все действия возвращают Promise. Ошибки и недоступные операции отклоняют Promise;
показа сообщения в CRM недостаточно для успешного завершения действия. После
закрытия просмотрщика хост освобождает подписки и отклоняет последующие вызовы.

Пагинируемые списки комментариев, задач, коммуникаций и истории не входят в контекст.
Заказы, файлы, теги и пользовательские поля также пока не включены в эту версию.

## Редактор: `ticket/edit`

Контекст предназначен для дополнения формы создания или редактирования обращения.
Он описывает текущий черновик, включая несохранённые изменения.
Библиотека объявляет точки `ticket/edit:common.before`, `ticket/edit:customer.after`
и `ticket/edit:issues.after` с контекстами `ticket/edit`, `ticket/edit:settings`,
`user/current`, `settings`, пользовательским контекстом `ticket` и action scope `ticket/edit`.
Подключение в хосте CRM выполняется отдельно; target-ы `ticket/view:*`
этот контекст не предоставляют.

```ts
import { useActions, useContext } from '@retailcrm/embed-ui-v1-contexts/remote/ticket/edit'
import { useContext as useEditorSettings } from '@retailcrm/embed-ui-v1-contexts/remote/ticket/edit-settings'

const ticket = useContext()
const settings = useEditorSettings()
const actions = useActions()

await ticket.initialize()
await settings.initialize()

if (!ticket.loading && !ticket.loadFailed && !ticket.saving && !ticket.pending) {
  ticket.set('description', 'Уточнить срок доставки')
  const key = await actions.addIssue()
  await actions.updateIssue(key, { typeId: 1 })
}
```

Расширение не управляет жизненным циклом формы. Методов `save`, `close`, `validate`,
`reset` и `refresh` нет. Валидацию, создание сущностей, сохранение обращения и
закрытие шторки выполняет CRM по действию пользователя. Успешный Promise действия
означает, что хост применил изменение к черновику и опубликовал результат;
сохранение в CRM он не подтверждает. Прямой `set` работает по существующему
контракту полей SDK: локальное обновление оптимистическое, отказ хоста передаётся
через обработчик отклонения, а подписки передают авторитетное состояние формы.

| Поля | Назначение и изменение |
|---|---|
| `id`, `mode`, `number` | Только чтение; режим `create` или `edit`, ID и номер нового обращения — `null` |
| `site`, `description`, `channel` | Изменяемые поля черновика; ссылки хост загружает и проверяет по ID, подпись расширения не считается авторитетной |
| `customer.id`, `customer.type` | Только чтение; типы `customer` и `customer_corporate` общие с заказами |
| `customer.name` | Имя выбранного клиента; ввод названия разрешён только для нового корпоративного клиента |
| `customer.lastName`, `customer.firstName`, `customer.patronymic`, `customer.email`, `customer.phone` | Профиль нового физического лица; выбранного существующего клиента через эти поля редактировать нельзя |
| `contact.id`, `contact.name` | Только чтение; выбранное контактное лицо корпоративного клиента |
| `contact.lastName`, `contact.firstName`, `contact.patronymic`, `contact.email`, `contact.phone` | Ввод профиля нового контактного лица в корпоративном режиме без выбранного контакта |
| `company.id`, `company.name` | ID только для чтения; ввод названия разрешён для новой компании в корпоративном режиме |
| `issues` | Вопросы черновика; коллекция и её элементы доступны только для чтения, изменения через действия |
| `orders`, `orderItems` | Выбранные заказы и позиции заказов, не результаты пагинируемого поиска; изменение через действия |
| `dirty`, `valid` | Только чтение: изменения всей шторки и результат локальной валидации черновика |
| `loading`, `loadFailed`, `saving`, `pending` | Только чтение: загрузка, её ошибка, сохранение CRM и блокировка конфликтующих изменений |
| `errors` | Только чтение: уже опубликованные ошибки формы; чтение не запускает валидацию |

В корпоративном режиме поля профиля `customer.*` пустые: внутренний профиль
редактора относится к контактному лицу и публикуется как `contact.*`. Для
физического лица поля `contact.*` и `company.*` пустые. Профильные строки имеют
тип `string`, пустой ввод — `''`. Наличие существующей связи запрещает изменение
её профиля, даже если поле в схеме допускает запись в других состояниях формы.
Хост проверяет режим, права и актуальную связь перед применением записи.

Каждый вопрос содержит `id: number | null` и `key: string`. Новый вопрос ещё не
имеет ID; для его изменения используется ключ в пределах текущего открытого
редактора. Формат ключа не является API: его нельзя разбирать или сохранять между
открытиями формы. Вопросы не адресуются индексом массива или ID вместо ключа.

`topic` — родительская тема, `subtopic` — выбранная подтема. В `updateIssue`
передаётся `subtopicId`; тему хост определяет сам. `responsible` содержит
пользователя или группу и соответствует терминологии просмотрщика. Внутренние
названия CRM `topic` для подтемы и `assignee` в публичный контракт не переносятся.
`sla` — снимок сохранённого SLA. Предварительный расчёт для нового вопроса
в `sla` не подставляется; `null` не означает отсутствия правил SLA.

| Действие | Изменение черновика |
|---|---|
| `changeCustomerType(type)` | Смена типа с согласованием зависимых полей клиента, контакта и компании |
| `selectCustomer(customerId)` | Выбор существующего клиента текущего типа с загрузкой доступных данных |
| `unlinkCustomer()` | Открепление клиента по правилам формы, включая очистку зависимых данных |
| `selectContact(contactId)` / `unlinkContact()` | Выбор или открепление контакта корпоративного клиента |
| `selectCompany(companyId)` / `unlinkCompany()` | Выбор или открепление компании корпоративного клиента |
| `addIssue()` | Добавление вопроса с настройками формы по умолчанию; возвращается локальный ключ |
| `updateIssue(key, changes)` | Частичное изменение вопроса: `typeId`, `subtopicId`, `responsible`, `statusId` |
| `removeIssue(key)` | Удаление вопроса из черновика |
| `addOrder(orderId)` / `removeOrder(orderId)` | Добавление или удаление выбранного заказа; удаление также убирает его выбранные позиции |
| `addOrderItem(orderItemId)` / `removeOrderItem(orderItemId)` | Добавление или удаление существующей позиции заказа; это ID позиции, не товара или предложения |

Пропущенное поле в `updateIssue` сохраняет значение, `null` очищает выбор.
Неполный или временно невалидный черновик допустим: исправления не запускают
сохранение. Цена и количество позиции из редактора обращения не меняются.
Неизвестные ключи вопросов, недоступные ссылки и запрещённые операции отклоняют
Promise. Повторное добавление заказа или позиции не создаёт дубликат.

Ошибки содержат сегменты `path`, машинный `code: string | null` и локализованное
`message`. Примеры путей: `[]` — вся форма; `['description']` — поле;
`['issues', key, 'subtopic']` — поле вопроса; `['customFields', code]` —
пользовательское поле. Непрозрачный ключ вопроса всегда занимает один сегмент.

## Настройки редактора: `ticket/edit:settings`

Все поля доступны только для чтения, действий у контекста нет:

| Поле | Назначение |
|---|---|
| `statuses`, `types` | Общие активные статусы и типы вопросов |
| `topics` | Темы с вложенными активными `subtopics` |
| `channels` | Общие активные каналы обращений |
| `creatable`, `editable` | Права пользователя на создание и редактирование обращений |
| `canCreateCustomer`, `canCreateCorporateCustomer` | Права создания клиентов соответствующего типа |

Справочник статусов не является списком разрешённых переходов конкретного
вопроса. Общие права не включают валидность и временные блокировки формы.
`valid` не гарантирует успешного сохранения или достаточных прав.

## Пользовательские поля редактора

Используется существующий механизм `remote/custom` с сущностью `ticket`,
ограниченной текущим экземпляром редактора. Хост должен явно предоставить
соответствующий custom-контекст в target-профиле редактора. Значения читаются и
меняются в черновике; `readonly` проверяется по схеме. Запись направляется в
штатный setter пользовательского поля редактора и согласует ошибки формы.
Даты передаются строками `YYYY-MM-DD`, дата со временем — ISO 8601, значения
справочников — кодами; объекты `Date` и сырые справочные объекты не передаются.

Теги, файлы, задачи, коммуникации, история и телефония в этот контракт не входят.
Некоторые штатные разделы сохраняются независимо от черновика, поэтому закрытие
без сохранения не обещает отката уже выполненных ими операций.
